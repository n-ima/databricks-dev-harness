# 目的に合わせた開発手順の改善設計

状態: 2026-09-16正式採用。[採用判断と限界](../decisions/ADR-0013-purpose-driven-delivery-adoption.md)を参照。要件は[受入条件](../requirements/2026-09-16-purpose-driven-delivery.md)。調査根拠は[比較記録](../research/2026-09-16-purpose-driven-delivery.md)。

## 設計判断

問題の中心は、工程がないことではなく、その工程で何を決めれば十分かが弱く、完成時の検査が途中の相談に混入し得ること。現在のskillには、配置だけの確認を許可する文と、全状態・契約・レビューを連続して要求する文が併存する。

1. 既存のexecution-planの「目的と検証可能な終了条件」を具体化する。別の進捗DB、全タスク必須の新JSON、新しい承認gateは作らない。
2. OPERATING_MODELを判断と証拠の案内に直し、固定順序の工程強制としない。並行設計、短い技術検証、既存の成果物再利用を明示する。
3. mock-uiを、途中の配置相談と正式な操作確認/承認に分ける。これは承認条件の緩和ではない。ui-check preview/mock、ui-approval-check、loop/権限制御の実装は変更しない。
4. 下書きは画面一覧・未決事項とともに記録する。全画面/対象状態を最終設計から落とさず、最初の相談までに全てを完成させない。全画面を少数のサンプルで代替して完了にすることも禁止する。
5. 本番予定の実部品・共通styleとfixtureを使う。入力状態やダイアログ等、配置判断に必要な最小コードは許容する。保存API/DB/厳密な業務計算は今回の判断に必要な場合だけ別目的に分ける。出来ない機能を動いたように見せず「試作・未接続」を表示する。
6. 実現性が配置を左右するtree/grid/認証等は、未決事項として期限を付け、小さな技術検証を先に行う。単に「後で」で隠さない。機密・権限の疑問は安全に保留し、相談を理由に実アクセスしない。
7. build/review/releaseの検証は成果の主張に合わせる。設計レビューに未実装backendの実行を要求せず、本実装の受入から必要な統合検証を消さない。Bundleを使わない正規の配備にも無関係なBundle生成を要求しない。

## 比較した案

| 案 | 判断 | 理由 |
|---|---|---|
| 近似HTMLへ戻す | 不採用 | 利用者が承認した見た目を別部品へ置換する問題が再発する |
| 全状態・全機能を実装してから初回確認 | 不採用 | 変わりやすい配置へ依存する手戻りを先に積む |
| 全てを詳細な新しい状態機械で強制 | 不採用 | 既存session/plan/approvalと重複し、工程目的より形式を優先する |
| タイマーだけで終了 | 不採用 | 判断材料不足でも終了し、目的の取り違えを直さない |
| 実部品による小さな表示と仕様の段階確定 | 採用 | 実部品のローカル表示・変更・全画面設計・新context再開を限定試行で確認。実Claude Code/Copilot反復比較と効率改善率は未検証 |

## 検証と反証

- 現行の正式承認拒否（近似HTML、未解決差異、自己/古いレビュー、状態不足、別app、古いhash）を維持する。
- 既存の承認不要な下書き表示を新たなgateで囲わない。全画面の設計完了と、表示できた一画面を混同しない。
- 実AppKit依存を用い、合成データだけの一覧/簡易入力/ダッシュボードの検証用表示を隔離領域で行う。既存案件のscript、環境変数、backendを起動しない。
- 別contextに初回表示の指示、修正指示、再開の指示を与える。目的外の本実装を始める、全画面を落とす、架空の承認を記録する等を失敗とする。
- model/provider別の比較は同一課題・版・条件で複数回行う。準備済みfixtureやCodexによる手順試験はClaude Code/Copilot実地試験の代用ではない。
- 時間/トークンは成功・手戻り・欠落・人の判断負担と共に測る。速いが画面/仕様が欠ける案は採用しない。速度改善の実測がなければ改善率を主張しない。

## 互換性と移行

CLIの形式、承認/品質契約、既存証拠は変更しない。案件で進行中のUIは再初期化せず、未確定な配置だけを既存部品で確認し直す。正式承認済み部分は不要に作り直さない。過剰に実装したコードも無断削除しない。

変更はcanonical skills/既存標準とtemplateへ反映し、providerコピーは生成する。正式配布時は新版・stamp・cacheなし更新検証を行う。作業branchの候補を、stamp済みmainの正式版や案件反映済みと表示しない。
