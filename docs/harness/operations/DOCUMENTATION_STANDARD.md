# 人が確認できる要件・設計・試験の標準

要件を伝える入口は、対象案件のClaude Code / Copilot Chat。自然言語と資料でよい。agentが資料を読み、案を作り、判断が必要な点だけ質問する。利用者にテンプレートや診断JSONの記入を要求しない。

## 言語と読みやすさ

人が読む可能性のある要件、設計、一覧、計画、試験観点/ケース、レビュー、運用手順、ナレッジ、チャット説明は日本語を標準にする。専門用語は初出で日本語の意味を補う。結論・何を確認してほしいかを先に書き、確定/案/未確定/適用外を区別する。

コード、SQL、JSONキー、ID、パス、API名、CLI、機械ログ、正確性が必要な公式引用は原語を維持する。翻訳が意味を損なう場合は原語と日本語の説明を併記する。長い二言語の重複文書や「日本語文字率」の一律検査は不要。schemaのdescriptionやOpenAPIのsummaryなど人向け説明は日本語にできる。入力資料の原文は保存し、勝手に書換えない。

既存の承認済み文書は一括翻訳しない。必要なら日本語の案内を追加し、正本の変更は影響・hash・再承認を確認する。過去の機械向けsession見出しは互換性のため残る場合があるが、新規本文・人への要約は日本語にする。

## 何を、どこで定義するか

| 工程/正本 | 利用者が確認する内容 | 詳細化の時期 |
|---|---|---|
| `docs/product/requirements/<feature>.md` | 目的、利用者、業務の通常/例外/取消、範囲/対象外、データの意味、品質/費用、受入条件 | 意図承認まで。未確定は質問に紐づける |
| `docs/product/architecture/<feature>.md` | 用語、機能、データ/項目、画面/遷移、外部境界、構成、リスク、運用 | 最初は案。対象sliceの実装判断に必要な定義は実装前に確定 |
| `docs/product/data/` / `ui/` / `interfaces/` | 長くなった定義だけ分離。主設計書から参照 | 同じ意味を本文と別紙で二重管理しない |
| `work/quality/<feature>.json` / `work/evidence/` / `work/reviews/` | テスト観点・ケースと要件等の対応、実行結果、別contextレビュー | 観点/ケースは実行前。結果と証拠は実行後 |
| `docs/product/runbooks/` / `knowledge/` | 利用手順、監視、復旧、更新、継続して使う知見 | 運用開始まで。責任者・確認日・見直し条件を付ける |

ハーネス自身の要件・設計・運用は `docs/harness/`。案件の説明をここへ混ぜない。初期生成は確定仕様ではない。手動で使う場合もひな型の `{{...}}` を実値へ具体化する。

## 定義の最低内容

| 対象 | 判断に必要な属性 |
|---|---|
| 用語集 | 日本語名、原語/別名、業務上の意味、含めない意味、根拠/責任者 |
| 業務利用 | 誰が、いつ/なぜ、何を入力し、通常/例外でどうなり、取消/訂正/引継ぎをどうするか |
| 機能一覧 | 機能ID、目的、役割/権限、入力/結果、例外、受入ID、画面/API/データとの対応 |
| データ一覧 | 論理名/物理名、目的、1行の粒度、正本/所有者、キー/関連/多重度、読取/更新、機密/保持/鮮度 |
| データ項目 | 日本語名/物理名、意味/出典、型/桁/単位、必須/NULL/既定値、許容値/制約、計算/端数/時刻帯、具体例 |
| 画面・遷移 | 画面ID、利用者/目的、機能ID、表示/入力項目、操作と遷移条件、引継ぎ値、戻る/未保存/取消、状態、端末/keyboard |
| 外部境界 | 相手/責任者、送受信方向、形式/版/入出力/頻度/件数、認証認可/実行主体、失敗/再送/上限、互換性/変更通知 |
| 試験 | 観点/リスク、要件等のID、環境、前提、手順、期待結果/判定値、証拠、未実行/失敗/成功の区別 |

HTTPはOpenAPI（入出力schema、operationId、正常/エラー例）を正本にする。生成可能なデータ辞書やAPI一覧は生成元・コマンドを記録し、手書きの二重定義にしない。非HTTPのイベント・ファイル・手作業の受渡しも境界として扱う。

相互参照は **業務→機能→画面/外部IF→データ項目→受入条件→テスト→証拠**。表にIDを置き、本文で同じ仕様をコピーしない。全リンクの意味と選択漏れは独立レビュー対象。図は、複数の遷移や信頼境界など表だけでは把握しにくい場合に限る。

## 未確定と省略

- 未確定: 答えがない。質問ID・判断担当・解決が必要な工程を記録。金額/税/権限/外部公開など業務結果や安全性を変える未確定は、そのsliceの実装前に解決する。
- 仮定: 案である。根拠・影響・検証方法を明記する。仮定を承認済みに置換しない。
- 適用外: 範囲外である根拠を記す。「未入力」「わからない」と区別する。
- 軽微な表記修正など振る舞い/データ/権限/APIが不変の場合、既存文書の差分と回帰証拠でよい。新しい全帳票や品質JSONを必須にせず、省略理由を計画に残す。既存の受入・独立レビュー・承認は省略しない。
- 新規機能/API/更新処理や振る舞い変更の本実装では[品質契約](DELIVERY_ASSURANCE.md)を用意する。APIのない分析でも要件/評価条件/費用/証拠を対応付け、HTTP欄は空にできる。全運用項目の適用判断は行う。初期の配置相談や隔離した小さな技術検証は、目的・対象・未接続/未検証・終了条件を既存設計/計画に残し、完成版の品質契約を表示前の条件にしない。本実装へ移るときの契約・承認は省略しない。

## UIの確認方法を選ぶ

全対象画面の一覧・配置・動作/遷移を設計書に残し、順次確認する。途中相談と正式な操作承認は別。[UI対応契約の運用](UI_RUNTIME_FIDELITY.md)に従い、初回の配置確認へ全画面の実装・backend・最終独立レビューを先取りしない。一部の画面だけで設計完了ともしない。

1. 画面がある案件は**設計段階からDatabricks Appsを既定**にする。AppKitは本ハーネスの既定UI実装。外部フロントエンドや別UI frameworkは、理由・対象・影響と利用者の明示選択を設計書へ記録してから使う。
2. 配置・ラベル・導線だけを先に確認する場合も、採用版の実コンポーネント・共通スタイル・架空データからローカル描画する。その描画から生成した静的HTMLは見た目の確認用に使えるが、独自CSSやspanで模した別画面を実装予定UIとして承認依頼しない。HTMLという拡張子だけでは適否は決まらない。
3. 入力・エラー・状態やkeyboard操作は、その同じアプリのfixture状態で確認する。既存AppKitアプリがあれば再利用し、確認後も同じコンポーネントを本実装へ引き継ぐ。新たな別アプリへの承認流用や再初期化をしない。
4. 必要なruntimeが未導入なら、画面一覧・項目・遷移・データ設計を先に進める。AppKit初期化に認証が必要なら選択/本人確認のgateで止まり、無関係なHTMLで代替承認しない。UIとテーブル/ER設計は並行して整合を確認し、UIの完成までデータ設計を省略しない。

静的な紙芝居の承認だけではui-mock gateを解除しない。[UI対応契約](UI_RUNTIME_FIDELITY.md)でApps/例外、対象アプリ、実部品・版・スタイル・fixture、全対象画面/状態、実行/視覚/操作証拠、別contextレビューを紐づける。未解決差異があれば未承認。スクリーンショットやhashだけでは実行・画面一致・人の承認を証明しない。API-onlyはUIを作らない。

## レビューと維持

対象sliceの本実装前に別contextで設計・観点を確認し、実装後に別contextで要件から反例を探す。書いた文書数を品質指標にしない。正常だけでなく拒否・競合・境界・再送・回復を対象に応じて照合する。AIの採点は真実の保証ではない。言語変更で誤訳した型/単位/条件がないかも確認する。

受入条件と意味レビューで具体性を確認する。診断JSONの整形成功、全欄への「未確定」、文書の存在だけでは実装準備完了や業務受入にならない。利用者へは日本語で確認対象、決定、残るリスク、次の作業を要約する。
