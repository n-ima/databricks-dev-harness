# 0.7.0 — 採用済み修正の配布と公開工程の一体化

## 変更と対象

- ハーネスのmain公開を「案件が取り込めるstamp済み新版の公開」まで一体化。日本語の開発手順、公開専用skill、source整合検査、main送信前guard、CIの版差検査を追加した。
- 0.6.1以後に採用されたDatabricks AppsのUI整合性検証を収録。既定のUI承認はApps上の本番と同じ部品/スタイルによるものとし、似せただけの独立HTMLを承認面にしない。詳細は`docs/harness/operations/UI_RUNTIME_FIDELITY.md`。
- 採用済みの承認範囲の記録・照合・撤回を収録。ただし、承認台帳だけで外部操作を許可したり、費用を強制制御したりはしない。
- 既知の5件の修正（Lakebase移行案内、pending gateを飛ばす完了、中断loopの再開、provider生成資産の保護、SQLのdollar quote判定）を収録。実装と未検証の境界を区別する。

## 既存案件への取り込み

進行中の案件でも更新できる。先に他エージェントの書込みを止め、信頼する新版をcloneまたはZIP展開して別フォルダーへ置く。ネット接続は適用時には不要。エージェントには「この案件のハーネスを、更新元のローカルフォルダーから更新して」と指示する。

旧0.6.1の更新器は新しい管理ファイルを理解しない場合がある。その場合は、**新版側の`tools/update-harness.mjs`と`--target`**を使う。これは標準skillが扱う橋渡し手順で、旧更新器のallowlistやstampを手編集しない。[安全な更新手順](../operations/SAFE_LOCAL_UPDATE.md)に従い、plan→競合/移行確認→apply→案件試験・レビューを行う。

案件要件/設計/コード、進行記録、package/lock、接続情報、独自skillは自動置換しない。管理ファイルへの案件独自変更は競合で停止する。`--force`や「案件固有を保持」の付け忘れに依存した上書きを行わない。

## 互換性と手動確認

- UI検証の前提を厳しくするため0.xのminorを上げた。既存のHTML資料を削除するのではなく、承認面として使っていた場合にAppsと本番部品への対応を再確認する。過去の承認/検証を新版で確認済みと読み替えない。
- 案件所有の`docs/product/standards/`や依存設定は保持する。新標準との差があれば案件側で差分をレビューして採否を決める。今回の公開対策はNode標準APIだけを用い、新規依存の追加は要求しない。
- 開発元の公開hookはハーネス保守専用。案件へ自動導入しない。案件Git pushとDatabricks配備は別操作である。
- 案件の既存session/task/承認記録は保持する。policyや成果物のhashが変わり検証が失効した場合は必要な範囲を再検証する。既存の人の採用判断を無理由に繰り返し要求しない。

## 検証範囲・復旧

配布準備ではsource完全一致、Git改行往復、0.6.1からのcacheなしsource/固定payload更新、案件保持・競合拒否・旧版不変、ローカル回帰と独立レビューを確認する。実行結果と対象hashの正本は`work/evidence/2026-09-16-publication-*`と`work/reviews/2026-09-16-publication-*`に残す。この案内の存在だけでは公開・全機能受入の証明にならない。

実案件適用、実Claude Code/Copilot、Databricks実環境、GitHub hosted CIは、それぞれの実行記録がない限り未検証。ハーネスはDatabricksへ配備しない。

旧0.6.1の固定配布物は保持する。適用前に案件の変更を保存し、適用時のbackupと計画を確認する。問題時は新規開発を止め、対象案件の記録とbackupから差分をレビューして復旧する。baselineの再生成・版戻し・旧版配布物の書換えで解決しない。公開後の修正は別の新版として出す。
