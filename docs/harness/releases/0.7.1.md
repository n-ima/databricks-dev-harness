# 0.7.1 — 工程の目的に合わせ、作り込みを先取りしない開発

## 変更

UIの配置相談と正式承認を区別する。Databricks Apps/AppKitの実部品と共通styleで配置・必要な局所操作を見せ、相談前に保存・認証・DBや業務計算を作り込まない。全画面のレイアウト・動作・項目・データ・未決事項は設計へ残し、段階的に確認する。正式承認と安全条件は従来どおり。

API契約、分析、AI評価、障害調査も「今の判断」「必要な成果と証拠」「今は行わないこと」「停止条件」に合わせる。skillsと既存標準/templateを修正し、Claude Code/Copilot向け資産へ同期した。UI評価課題を初回配置→修正→全画面設計→履歴なしの再開へ強化。承認・権限・CLI schemaは変更しない互換保守版である。

## 既存案件への更新

信頼する0.7.1のcloneまたはZIP展開先を案件と別の場所に用意する。ネットに接続できない案件は、検証済み展開フォルダーを持ち込めばよい。案件側のチャットで「この案件のハーネスを、更新元フォルダーの0.7.1へ更新して」と依頼する。[安全な更新手順](../operations/SAFE_LOCAL_UPDATE.md)のplan→競合・移行確認→apply→案件試験を使う。古い入口では新版側の`tools/update-harness.mjs`と`--target`を使う。旧版のallowlistやstampを手編集しない。

案件固有の要件・設計・コード・進捗・package/lock・接続設定・独自skillは保持する。管理ファイルの独自変更は競合で停止する。先に書込み中agentを止め、変更を保存する。開発元の公開だけでは案件へ自動反映されない。

## 移行時に確認すること

- 既にある実AppKit画面を使い、再initしない。正式承認済み部分を不要に作り直さず、未確定な配置だけを確認する。
- `docs/product/standards/`、既存の案件設計書や計画は案件所有のため自動置換しない。新しいskillと`docs/harness/operations/`にある段階別方針を読み、旧文書が初回配置に完成版の試験を要求していれば差分を確認する。
- 全画面の一覧・動作・データ定義・未決事項の保存は省略しない。配置確認を正式UI承認や動作保証へ読み替えない。
- 作り込み済みコードも無断削除しない。適用backupと計画を保持し、不具合時は追加開発を止め対象差分をレビューして復旧する。旧版の固定配布物を書き換えない。

## 検証範囲
