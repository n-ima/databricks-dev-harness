# 設計・検証・運用をつなぐ品質契約

## 目的と範囲

自然言語の要求から、要件、外部契約、リスク、テスト、証拠、運用引継ぎまでの不足を発見する。最高水準を目指すが、世界順位や完全網羅を自己認定しない。既存ハーネスを捨てず、現在の完了・承認・予算制御は維持する。

今回の許可は再調査、設計、ローカル改善候補、検証まで。新しい評価基準の正式採用、既存案件変更、remote push、実Databricks操作、課金モデル実験は含めない。今回のcheckerは参考診断であり、既存のcompletion receiptの代替ではない。

## 候補の受入条件（未承認）

- AC-01: 最新一次情報と現行コードの対応を記録し、既実装・不足・未検証を分離する。
- AC-02: 品質契約の重複ID、未定義参照、要件・リスクからテストへの未対応、期待結果不足をローカル診断で検出する。
- AC-03: API操作と対象テスト、正常・拒否ケース、認証認可・再送・互換性の検討不足を検出する。適用外は理由を要求する。
- AC-04: 実行証拠の不足と古いsnapshotを検出し、ローカル試験を実環境試験の代替として認めない。
- AC-05: 運用責任、監視、復旧、データ保護、費用、依存更新の検討有無を診断する。設計段階の未実行は正直に残す。
- AC-06: 新しいcontextで仕様・テスト観点と実装を独立レビューし、指摘・修正・再検証を残す。context ID等の記録だけでは本人認証や意味的独立性を保証しない。
- AC-07: 診断はファイル変更、外部接続、記載commandの実行、既存gate解除を行わない。不正入力・範囲外path・symlinkを拒否する。
- AC-08: 両providerの固定条件比較計画、未知ケース、費用と人の介入の測定方法を定義する。未実行の比較を成功扱いしない。

## 人の判断

候補の設計・検証結果を確認してから標準フローへの正式採用を判断する。全世界の全手法の同時優越、すべての入力の完全網羅、無条件の本番自動実行は受入条件にしない。
