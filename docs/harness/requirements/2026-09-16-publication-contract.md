# 案件が取り込める状態までをハーネス公開の完了条件にする

利用者は、main反映が更新可能な配布版になっていなかった問題について、ハーネス開発手順・スキル・再発防止と、開発目的に必要な対策を指示した。source pushとstampを別依頼に分割せず、一つの公開作業として扱う。単なる注意書きではなく、拒否検査と実際の更新経路で検証する。

## 受入条件

- PUBC-01: ハーネス開発から案件利用までの手順、状態、責任、証拠、main公開の完了条件を日本語で定義し、自然言語の公開依頼を専用skillへ導く。案件のDatabricks配備と区別し、同じ採用判断を再要求しない。
- PUBC-02: 公開前の読取専用検査がstamp欠落/古さ、管理ファイルの追加漏れ/削除/改変、版不一致、同一版の内容変更を検出する。旧cached releaseの成功を最新sourceの合格へ読み替えない。
- PUBC-03: 通常のmain pushをローカルguardで検査し、CIにも同じ検査を接続する。送信commitと作業treeの取り違え、別refからmainへのpush、main削除、既存hookの上書きを防ぐ。回避可能性とGitHub側保護の限界を説明する。
- PUBC-04: 初期化済みの合成案件を使い、cacheなしの配布sourceと固定配布物からの更新、案件固有の保持、競合停止、旧版保持を試験する。利用者にstampの手編集やforceを要求しない。
- PUBC-05: 変更スキルの両provider生成コピー、回帰試験、別contextの設計/実装レビューと現実的な依頼でのforward確認を記録する。実環境未検証や公開未実施を成功と混同しない。

## 対象外

実案件・Databricks・モデル課金・秘密情報・GitHub権限変更は行わない。今回の作業は対策の実装とローカル検証。承認済みのコードを新版にする準備を含むが、この指示だけでGitHubへ追加pushしたとは扱わない。ハーネス自体はDatabricksへ配備しない。
