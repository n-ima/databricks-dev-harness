02 / START

最初の準備を、ひとつの流れに。

ハーネス本体をGitHub Templateにし、開発対象ごとに別repoを作ります。プラグインは補助配布の候補。コード・設計・テスト・CI・記録まで揃える本体はテンプレートです。

  1. 提供者：テンプレートを登録

    組織・公開範囲を決めてpush。template設定、main保護、必須CI、独立レビュー、本番Environmentの承認者を設定します。

  2. 利用者：案件を作成

    GitHub CLIでログインし、下のコマンドの組織・案件・パス・workspace・profileを置き換えます。

  3. 本人：認証・エージェント選択

    OAuthブラウザー承認を行い、VS CodeでClaude CodeまたはCopilotのAgentモードにサインインします。

テンプレート側のcloneから実行。GitHubの指定repoを新規作成します。

gh auth login
.\scripts\new-project.ps1 -Template ORGANIZATION/databricks-dev-harness -Repository ORGANIZATION/sales-operations -LocalPath D:\projects\sales-operations -Profile sales-dev -HostUrl https://YOUR-WORKSPACE.cloud.databricks.com -Authenticate -InstallPrerequisites -InstallExtensions

GitHubのUse this templateで作成・cloneしたrepo内で実行。

.\scripts\setup.ps1 -ProjectName sales-operations -Profile sales-dev -HostUrl https://YOUR-WORKSPACE.cloud.databricks.com -Authenticate -InstallPrerequisites -InstallExtensions
code .

Node.js 22以上・Git・Python 3.10以上（契約試験用）・Databricks CLI 1.6以上2未満を先に用意。Databricks RuntimeのPython版は案件ごとに別途合わせます。

bash scripts/setup.sh --project-name sales-operations --profile sales-dev --host https://YOUR-WORKSPACE.cloud.databricks.com --auth
code .

インストールはopt-in。既存の古いツールを黙って更新しません。支払い、権限付与、本番デプロイは行いません。

workspace未準備でも進められる？

Nodeと同梱Skillsで要件整理・設計まで進められます。公式AppKitの初期化はfixtureモックでもCLIと開発workspace認証が必要です。profileとhostを明示し、業務データ・live pluginは接続しません。

npm ci --ignore-scripts
npm run setup -- --project-name sales-operations --skip-agent-skills
接続確認は何を検証する？

明示profileとhostの一致、OAuth結果、workspace到達性、current-user。認証成功だけではresource権限は保証されません。catalog/schema/team_root等を設定しBundleをstrict validateします。

npm run harness:doctor -- --profile sales-dev --json
databricks bundle validate --strict -t dev --profile sales-dev

tokenをrepoへ保存しません。DEFAULTや唯一のprofileも自動選択しません。

03 / DAILY WORK

特別な呪文は、いりません。

資料をrepoに置き、目的・利用者・制約を普通に伝えます。エージェントが既存記録を探し、適切な手順と必要なSkillsを読み込みます。

営業責任者が地域別の売上異常を見つけるアプリを作って。資料はdocs/product/intakeに置いた。まず架空データで操作できるモックを見せて。要件と設計から進めて。
01意図を固める資料・質問・受入条件
HUMAN要件・モック承認重要な意味と画面を確認
02小さく作る実装・テスト・修正
03別の目で確かめる独立検証・証拠・記録

AIが進めること

既存調査、要件・設計のドラフト、fixtureモック、承認済み範囲の実装、機械チェック、失敗修正、checkpoint、知識の整理。

人が決めること

業務上の正しさ・対象範囲、未確定の重要事項、モック、機密データと権限、破壊的変更、本番反映。

「調べるだけ」「レビューだけ」の依頼から、勝手に実装・デプロイへ進むことはありません。

作るたびに、選び直さない。

DATA

登録・更新処理

Delta / Lakeflow Jobs。主キー、重複、遅延、再実行、照合を先に契約化。transactional CRUDはLakebase。

INTELLIGENCE

Genie

参照範囲とspace定義を管理。代表質問・言い換え・曖昧さ・権限のbenchmarkを持つ。

ANALYTICS

分析ダッシュボード

AppKit UIのchart/tableを使うrich app。共有KPIはMetric Viewsで意味を揃える。

APPLICATION

業務アプリ

AppKit / React / TypeScript。Lakebase Autoscalingで更新、認可・競合・監査を設計。

AppKit UIECharts系 chartsTanStack系 tablesVitest / Playwright

固定versionの公式manifestからscaffoldし、APIは生成後のinstalled docsを確認します。mockは本番用部品＋架空データ。画像だけで終えず、空・読込・エラー・権限不足・部分データ・狭い画面も確認します。別のlibraryが必要なら理由をADRに残します。

05 / DURABLE MEMORY

会話が変わっても、続きから。

Chatは入口。記憶はファイル、完了の根拠はテストと証拠です。ClaudeからCopilotへ切り替えても、同じ要件・設計・checkpointを読みます。

docs/harness/ハーネス自身の要件・設計・調査・ADR・運用・知識
docs/product/開発対象の要件・設計・UI・データ契約・運用・知識
work/sessions/目的・確認済み状態・判断・証拠・次の行動・ブロッカー
work/evidence/ · reviews/実際の結果と独立検証。自己申告の完了を分離
work/loops/ · approvals/反復の残予算・停止理由・人の決定・内容hash
前回の売上アプリを再開して。記録を再確認し、次の未完了項目から進めて。

ナレッジには出典・確度・適用範囲・再確認日を付けます。繰り返す失敗は実行可能なチェックへ。生チャット全文・token・本番データを自動で永続化しません。

06 / IMPROVEMENT

改善にも、合格条件を。

  1. 失敗を残す最小の再現例と人の手戻り
  2. 小さく変えるtest・schema・hook・generator
  3. 同じ課題で測るproviderごと3回以上・独立判定
  4. 差分で配るversion固定・conflict検出・backup

通常はassisted mode。headless loopはopt-inで、反復数・壁時計・process時間を制限します。pending gate・policy変更・失敗で停止。未記録の中断反復を黙って再実行しません。費用のsoft limitをhard capとは扱いません。

更新は案件側の変更を保護します。案件コード、product設計、work記録、接続設定はupdaterの所有外です。snapshot作成だけで公開や品質認定はされません。

07 / BEFORE PRODUCTION

できたことと、確かめること。

ローカル実装 ≠ 本番導入済み。

実workspaceの権限と接続、Claude/Copilot各hostでの実行、実モデルのgolden trials、GitHub側の保護設定・OIDC、実データ/UIの受入試験は、対象環境を指定したうえで確認します。

hookやhashは改変・誤操作の検出に有用ですが、同じOS権限で動くagentへの完全なsecurity境界ではありません。開発限定credentials、OS/container隔離、branch protection、CI、Environment承認を組み合わせます。

「完了」はどう決まる？

受入条件の全項目に、実在する証拠・独立review・変更されていないhashが必要です。not-runはpassになりません。業務上の妥当性とreviewerの本人性は人・CI・組織側の管理で担保します。

どこから始めればいい？

まず小さい1案件をテンプレートから作り、要件→mock→dev検証を一巡します。workspace URLと開発profile、案件repo、利用providerを指定すれば、その環境の導入確認へ進めます。
