02 / START

案件フォルダーを用意してから、setup。

空のディレクトリでsetup.shを実行するだけ、ではありません。

テンプレートから案件repoを作成 → clone → そのrepoのルートにあるsetupを実行します。揃うのは開発ハーネスと接続設定です。アプリ本体・依存ライブラリ・Databricksリソースや権限・deployは、その後の工程です。

Claude Code・GitHub Copilotは利用可能という前提です。新しいプラグインの導入やエージェントの再インストールは不要。ハーネス本体のprivate templateは作成済みなので、これから作りたい製品用の別repoを作ります。

  1. 1. 案件repoを作る

    例：n-ima/sales-operations。同じ製品のアプリ・データ処理・Genieは一緒に管理できます。

  2. 2. clone先でsetupする

    例：D:\projects\sales-operations。apps/内でも、元ハーネス内でもありません。

  3. 3. 値を指定して依頼する

    本人がOAuth承認。データ利用時にCatalog等を選択し、同じ案件をVS Codeで開いて自然言語で依頼します。

案件の作り方を1つ選ぶ

現在のハーネス本体のcloneから実行します。LocalPathの案件ディレクトリは先に作りません。 空でも既存のパスは拒否します。GitHub CLIが必要で、未ログインの場合のみ先にgh auth login。次のnew-projectは新規private repoを作成します。

Set-Location D:\projects\databricks-dev-harness
gh auth status
.\scripts\new-project.ps1 -Template n-ima/databricks-dev-harness -Repository n-ima/sales-operations -LocalPath D:\projects\sales-operations -ProjectName sales-operations -Profile harness-dev -HostUrl https://dbc-3fb0b9a2-66bb.cloud.databricks.com -Authenticate -InstallPrerequisites
Set-Location D:\projects\sales-operations
npm ci --ignore-scripts
npm run harness:check
code .

GitHubでUse this template → Create a new repositoryを選択。例：Owner n-ima、Name sales-operations、Privateで作成します。clone済みならclone行を省略し、案件フォルダーへ移動してsetupします。

Set-Location D:\projects
gh repo clone n-ima/sales-operations D:\projects\sales-operations
Set-Location D:\projects\sales-operations
.\scripts\setup.ps1 -ProjectName sales-operations -Profile harness-dev -HostUrl https://dbc-3fb0b9a2-66bb.cloud.databricks.com -Authenticate -InstallPrerequisites
npm ci --ignore-scripts
npm run harness:check
code .

GitHubのUse this templateでprivateな案件repoを作成してから、作業する親フォルダーで実行します。setup.shはOSツールをインストールしません。 Node.js 22以上・Git・Python 3.10以上・Databricks CLI 1.6以上2未満を、このshellで使えるようにしておきます。

git clone https://github.com/n-ima/sales-operations.git
cd sales-operations
bash scripts/setup.sh --project-name sales-operations --profile harness-dev --host https://dbc-3fb0b9a2-66bb.cloud.databricks.com --auth
npm ci --ignore-scripts
npm run harness:check
code .

repo名・profile名を決めてから実行します。Windowsの -InstallPrerequisites は不足ツールの導入への明示同意。既存の古い版は黙って更新しません。認証オプションを付けた場合は本人がブラウザー承認します。エージェント導入済みなので -InstallExtensions は省略しています。

setupでできること・別途行うこと

setupが整える

案件名のproduct.config.json、rootのdatabricks.ymlひな型、両エージェントのSkills、記録用ディレクトリ、元テンプレートの更新基準。指定したprofile/hostの接続確認後、非秘密のメタデータを.harness/local.jsonへ保存します。

setupでは行わない

npm ci、AppKitアプリ生成、アプリ固有の依存導入、Catalog/Schema・warehouse・Lakebase・Genie・Apps作成、権限付与、データ更新、deploy。アプリの依存は生成後のlockfileに従ってエージェントが導入します。

Connected ...、Harness check passed.、Setup complete.を確認します。これで要件・設計と接続確認へ進めますが、Bundle検証や実行準備の完了とは別です。

データ利用前：Catalogと配置先を保存する

DatabricksのCatalog → catalog → schemaで対象を選びます。案件repo内に.databricks/bundle/dev/variable-overrides.jsonを作成し、次の例のcatalog/schemaを確認済みの実名へ置き換えます。setupはこのファイルを作りません。作成はエージェントに任せられます。

{
  "catalog": "workspace",
  "schema": "sales_dev",
  "team_root": "/Workspace/Shared/test/dev-harness",
  "dev_suffix": "my-pilot-01"
}

workspaceとsales_devは例で、存在や権限を確認した値ではありません。ファイルはGit対象外。tokenは書きません。.envは自動読込されず、別shellへexportが引き継がれる保証もないため、このtarget別ファイルを使います。

team_rootを設定しても、devの配置先は変わりません。

既定のdevは /Workspace/Users/.../.bundle/案件名/dev/作業ID。team_rootを使うのはtest/prodです。最初はUsers配下のdevを維持するのが簡単です。devも添付のShared配下にしたい場合だけ、実践ガイドの5-3に従い、案件のdatabricks.ymlにあるtargets.dev.workspace.root_pathを変更します。

値と必要なresource定義を整えた段階で、案件rootから確認します。要件整理を始める前にすべてのBundle検証を終える必要はありません。設定未完でstrict validateが止まった場合は、指摘内容をエージェントと解消します。以下はdeployやデータ更新を行いません。

databricks workspace get-status /Workspace/Shared/test/dev-harness --profile harness-dev
databricks bundle validate --strict -t dev --profile harness-dev
npm run harness:doctor -- --profile harness-dev --json

フォルダー参照・認証の成功は、書込権限やアプリ稼働の証明ではありません。生成後のapps/<app-name>/は独立Bundleなので、rootの変数は自動継承されません。

アプリ・処理ごとのDatabricks準備は？

データ処理は対象Catalog/Schema・入力・computeと読書き権限。分析アプリはSQL warehouseとデータ権限。Genieは参照データ・warehouse・質問と期待結果。入力系アプリはLakebaseのproject/branch/databaseを選択します。既存利用か新規作成かは人が決め、最初から全部作る必要はありません。

warehouse IDはSQL → SQL Warehouses → 対象 → Connection DetailsにあるHTTP pathの/warehouses/より後です。workspace IDやフォルダーIDとは別で、setupの引数ではなく後のscaffoldに指定します。App専用service principalの権限も個人の権限とは別に確認します。

添付のFree Editionだけでよい？

非商用のサンプル検証を始める環境として考えます。2026-09-04確認の公式案内では非商用限定・SLAなし、serverless限定、SQL warehouse 1つ、Apps最大3つで最大24時間後停止、Lakebase 1 projectなどの制限があります。業務本番や全AppKit pluginの動作を保証するものではありません。公式の制限を見る。

workspace未準備でも進められる？

テンプレート取得済みの案件repoで、Nodeと同梱Skillsを使って要件・設計を進められます。接続もUIアプリ本体もまだできていない状態です。公式AppKitの初期化はfixtureモックでも明示dev profile/hostと認証が必要です。

npm ci --ignore-scripts
npm run setup -- --project-name sales-operations --skip-agent-skills
new-projectやsetupが途中で止まったら？

repoやcloneができている場合、new-projectは繰り返さず、案件repo内のsetupだけを再実行します。古いツールは会社指定の方法で更新し、必要なら新しいターミナルを開きます。認証だけならnpm run harness:connect -- --profile harness-dev --host https://dbc-3fb0b9a2-66bb.cloud.databricks.com --authで再確認。Catalog等のMissing variableは変数ファイルを確認し、権限不足をtoken貼付で回避しません。

最後に、同じ案件フォルダーでエージェントへ

この案件のAGENTS.mdとactive sessionを確認して。profileはharness-dev、開発はdevのUsers配下。営業データの分析アプリを作りたい。要件と設計から始め、架空データのモックを見せて。本データ接続・権限変更・deployは承認を待って。

CLIのprofileは本人が決めた名前に合わせます。Claude CodeとCopilotは同じ案件repoを開いて利用し、切替時は先の作業をcheckpointしてから記録を引き継ぎます。

AIが進めること

既存調査、要件・設計のドラフト、fixtureモック、承認済み範囲の実装、機械チェック、失敗修正、checkpoint、知識の整理。

人が決めること

業務上の正しさ・対象範囲、未確定の重要事項、モック、機密データと権限、破壊的変更、本番反映。

「調べるだけ」「レビューだけ」の依頼から、勝手に実装・デプロイへ進むことはありません。

05 / DURABLE MEMORY

会話が変わっても、続きから。

Chatは入口。記憶はファイル、完了の根拠はテストと証拠です。ClaudeからCopilotへ切り替えても、同じ要件・設計・checkpointを読みます。

docs/harness/ハーネス自身の要件・設計・調査・ADR・運用・知識
docs/product/開発対象の要件・設計・UI・データ契約・運用・知識
work/sessions/目的・確認済み状態・判断・証拠・次の行動・ブロッカー
work/evidence/ · reviews/実際の結果と独立検証。自己申告の完了を分離
work/loops/ · approvals/反復の残予算・停止理由・人の決定・内容hash
前回の売上アプリを再開して。記録を再確認し、次の未完了項目から進めて。

ナレッジには出典・確度・適用範囲・再確認日を付けます。繰り返す失敗は実行可能なチェックへ。生チャット全文・token・本番データを自動で永続化しません。

06 / IMPROVEMENT

改善にも、合格条件を。

  1. 失敗を残す最小の再現例と人の手戻り
  2. 小さく変えるtest・schema・hook・generator
  3. 同じ課題で測るproviderごと3回以上・独立判定
  4. 差分で配るversion固定・conflict検出・backup

通常はassisted mode。headless loopはopt-inで、反復数・壁時計・process時間を制限します。pending gate・policy変更・失敗で停止。未記録の中断反復を黙って再実行しません。費用のsoft limitをhard capとは扱いません。

更新は案件側の変更を保護します。案件コード、product設計、work記録、接続設定はupdaterの所有外です。snapshot作成だけで公開や品質認定はされません。

07 / BEFORE PRODUCTION

できたことと、確かめること。

ローカル実装 ≠ 本番導入済み。

実workspaceの権限と接続、Claude/Copilot各hostでの実行、実モデルのgolden trials、GitHub側の保護設定・OIDC、実データ/UIの受入試験は、対象環境を指定したうえで確認します。

hookやhashは改変・誤操作の検出に有用ですが、同じOS権限で動くagentへの完全なsecurity境界ではありません。開発限定credentials、OS/container隔離、branch protection、CI、Environment承認を組み合わせます。

「完了」はどう決まる？

受入条件の全項目に、実在する証拠・独立review・変更されていないhashが必要です。not-runはpassになりません。業務上の妥当性とreviewerの本人性は人・CI・組織側の管理で担保します。

どこから始めればいい？

まず小さい1案件をテンプレートから作り、要件→mock→dev検証を一巡します。workspace URLと開発profile、案件repo、利用providerを指定すれば、その環境の導入確認へ進めます。
