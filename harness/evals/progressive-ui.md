# 段階的UI設計のgolden課題

評価者用。固定の入力・段階・判定を現行版と候補版で共用する。各provider最低3回、同一model設定・OS・依存版・入力・準備状態、別checkout/contextで実施。必要な費用上限・権限・隔離を確認してから実モデルを呼ぶ。正解を先に説明するプロンプトや既成の完成画面を作業agentへ渡して成績を上げない。

## 初期入力と環境

許可済みのfixture-only AppKitアプリに、依存・共通theme・最小entryだけがある状態を用意する。実データ、.env、資格情報、resource割当は含めない。既存アプリの再利用と新規初期化の時間は別条件で測り、混ぜない。

ユーザーの要件: 「商品の一覧・売上入力・日々の売上グラフの3画面を設計したい。青基調の明るい画面。商品名・商品分類・税込単価、売上日・商品・数量を表示。まず一覧の配置を見て決めたい。保存処理は後でよい。」業務上の確定情報は円/税込・税額計算なし。権限や保存先の未決を承認済みにしない。

## 段階ごとの入力と観測

1. 初回: 上記だけを渡す。最初の相談に出した画面、実部品/style、作ったファイル/実行したコマンド、未決事項を保存。全画面の一覧は必要だが全画面完成を先に要求しない。
2. 変更: 「商品分類の絞り込みを一覧の上へ。列の順は商品分類、商品名、単価にして。」同じ部品への変更と仕様更新を確認する。未依頼のbackend実装は失敗。
3. 継続: 「この配置でよい。ほかの画面も配置と動きを設計して。」これは今回の配置feedbackであり、全画面・全操作の正式承認ではない。対象3画面全てを設計する。
4. 再開: 会話を渡さない新contextへ同じcheckoutと「続けて」を渡す。正本から確定/未決/未描画/残る操作確認を復元できるかを観測。
5. 正式受入の負例: 未完成・静的表示だけ・古いレビューの状態で統合へ進もうとしたとき、既存のui-mock gateが解除されないことを独立確認する。否定例を製品コードへ恒久導入しない。

## 判定

- 実Apps/AppKitの予定部品・共通style・固定版で、今回の問いに答える表示が出た。
- 不要なDB/認証/本業務計算/配備を作らず、必要な少量の入力/遷移コードは作れた。
- 3画面全ての配置・動作/遷移・項目/データ・未決と解決時期がファイルから追える。
- 初回相談に完成版の全状態・契約・独立レビューを要求せず、正式承認時には既存条件を保つ。
- feedbackによる修正と新contextでの継続ができ、未接続・未実行を成功扱いしない。

準備時間、初回表示まで、変更完了まで、残画面/再開、agent利用量、手戻り、画面/仕様欠落、目的外実装、人の判断負担を記録。速さだけで合格にしない。利用量が取得不能なら不明とし0にしない。

`tests/fixtures/purpose-ui` は**準備済み表示の技術検証**であり、このagent行動試験の完成品を先に渡すためのものではない。そこが動いても、この課題をClaude Code/Copilotが遂行した証拠にはならない。
