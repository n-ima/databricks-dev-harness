## 画面と利用者の判断

画面ID: UI-01。主操作は「明細を追加」。対象商品と入力した数量・税込単価が正しいことを追加前に確認できるようにする。

| 入力・表示 | 役割と振る舞いの案 |
|---|---|
| 商品分類 | 必須の選択。分類を変えたら商品選択をクリアし、候補を絞る |
| 商品 | 必須の選択。分類を選ぶまでは選択不可。商品名を識別できる表示 |
| 数量 | ラベル付き数値入力。初期値1は旧資料を踏まえた案。許容小数・上限は未確定 |
| 税込単価 | ラベル付き数値入力。税を含む1単位当たりの金額。追加の消費税計算は行わない案 |
| 明細を追加 | 入力検証に成功したときだけ明細を1行追加。失敗時は値を保持 |
| 明細一覧 | 追加された商品分類・商品・数量・税込単価を確認。初期状態では「まだ明細がありません」 |

採用方針はDatabricks Apps / AppKit。AppKitのselect系・input系・button・table・form feedbackの実部品を調査して対応付ける。実package、版、API、entry、共通styleが未提供なので、具体的なimport名やpropsを推測しない。

PC幅では入力順を保って見渡せる配置、狭い幅では同じ順番の縦配置を検討する。実部品での描画前に寸法や見た目の一致を確定しない。明細はAppKitのtableを優先し、狭い幅の可読性・横スクロールは実画面で検証する。

keyboardは商品分類→商品→数量→税込単価→追加の順。各入力とlabelの関連、選択・buttonの操作、エラー箇所へのfocus、エラー通知、追加結果の通知を試験する。追加後の入力保持・focus移動は下記未確定事項を解決してから固定する。

## データ設計案（物理DBは作成しない）

UIと並行して、1行の意味と関係を定義する。永続化方式、resource、権限、APIは今回対象外。

| 論理データ | 1行の粒度 / 主な項目 | 関係 |
|---|---|---|
| 商品分類 | 1分類。category_id: string、category_name: string | 商品に対して1対多 |
| 商品 | 1商品。product_id: string、category_id: string、product_name: string | 1分類に所属する案 |
| 見積 | 入力中の見積1件。quote_id: 画面内ID | 明細に対して1対多 |
| 見積明細 | 追加操作で作る1行。line_id、quote_id、product_id、quantity、unit_price_tax_inclusive | 商品に対して多対1 |

商品分類は商品の参照先から表示し、明細内の独立した分類入力と矛盾しないようにする。数量と単価の業務型・小数精度は未確定。通貨はJPYを候補とするが未承認。金額を実装する際は浮動小数の誤差を避ける表現を規則決定後に選択する。過去の商品名や単価の履歴保存は将来の永続化設計で決める。

必須性の案: category_id、product_id、quantity、unit_price_tax_inclusive。NULLや空欄のまま追加できない。商品は選択分類の候補に含まれることを検証する。

合成データ案: C-01「文具」/ P-01「テストノート」/ P-02「テストペン」、C-02「候補なし分類」。数量1・税込単価100は入力例であり、商品の正規価格や税率ではない。実データ・認証情報は含めない。

## 遷移と例外の案

| 状態ID | 状態 / 操作 | 期待する振る舞い |

1. 利用者が開発用workspaceとprofileを選ぶ。製品要件と未確定事項を必要な範囲で確定する。

4. 実部品の描画、主要操作、対象状態、desktop/narrow、keyboardを検証して観察証拠を記録する。
5. UI対応契約と独立レビューを揃え、人が実画面を確認してからui-mock承認を記録する。後の統合でも同じアプリを拡張する。
